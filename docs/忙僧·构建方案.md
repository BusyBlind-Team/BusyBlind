## 一、五个前置设计决断

后面所有内容都基于这五条，建议先对齐：

1. **听觉是第一交互通道，视觉是辅助。**
   所有玩法必须在"屏幕熄灭 / 用户闭眼"的前提下成立；屏幕上的内容是"睁眼时的奖励"，不是"闭眼时的必需"。

2. **一切时间以音频时钟为准。**
   不使用帧循环、不使用 `setInterval` 做判定。

3. **修行是插件，不是页面。**
   每个修行实现同一份契约，主程序不认识任何具体修行。

4. **本地优先（local-first）。**
   全部数据先写本地，服务器只是同步与社交层；断网时除加好友外功能完整。

5. **修为只由"真实完成的专注时间"产生。**
   任何可挂机、可后台刷的口子都视为 bug。
   ⚠️ 注：策划案/框架提示词中"每日抽签 +10 修为"与本条字面冲突，处理建议见 [6.3](#63-四个按钮方块签成禅友) 与附录 #9。

## 二、技术栈

**推荐组合：Flutter + 原生音频插件**

| 层面 | 选型 | 说明 |
|---|---|---|
| UI / 逻辑 | Flutter | 单套代码双端；Low-Poly 风格的几何图形用 `CustomPainter` 直接画，比切图省事且分辨率无损（框架提示词要求按钮方块为 Low-Poly 风格） |
| 背景长音轨 | `just_audio` | 潮汐、白噪声等长音频 |
| 短音效 | `soLoud` 或原生 AVAudioEngine / Oboe 封装 | 木鱼声、叮/咚、磬 |
| 本地存储 | SQLite（Drift） | 存修行记录、花瓣与图鉴；SharedPreferences 只存轻量偏好 |
| 状态管理 | Riverpod | — |
| 后端 | Supabase | Postgres + Auth + Realtime，省掉自建服务器（好友修为查看、花瓣交换用 Realtime） |

**为什么不选 Unity**：包体大（起步 40MB+），冥想类应用启动速度和体积敏感，而本产品几乎没有 3D 与物理需求。

**为什么不选 React Native / Web**：短音效低延迟触发是本产品的命门，JS 桥接层在这一点上不可靠。

**关键取舍**：短音效播放必须走原生层，且预加载进内存池，禁止播放时解码。木鱼玩法需要支持每秒一次、连续敲击全程无卡顿、无音头截断。

## 三、架构分层

```
┌─────────────────────────────────────────────┐
│  Shell 层：三页签容器 / 修·僧·我 导航         │
│   主界面按钮（签·成·禅·友）/ 教程             │
├─────────────────────────────────────────────┤
│  Practice Host（修行宿主）                   │
│   · 生命周期调度  · 中断恢复  · 结算收口     │
├──────────────┬──────────────┬───────────────┤
│ Practice     │ Practice     │ Practice      │
│ 木鱼         │ 数雨         │ 听潮 钓花 过河│  ← 插件
├──────────────┴──────────────┴───────────────┤
│  Core Services（所有修行共用）               │
│   AudioClock  · SoundBank  · EventScheduler  │
│   InputCapture · SessionRecorder · Haptics   │
├─────────────────────────────────────────────┤
│  Domain：修为经济 / 成就引擎 / 花瓣图鉴       │
│         / 好友社交                           │
├─────────────────────────────────────────────┤
│  Data：本地 SQLite  ⇄  同步引擎  ⇄  云端      │
└─────────────────────────────────────────────┘
```

**要点**：修行插件**不允许**直接访问 Domain 层。它只能向宿主返回一份结果对象，由宿主统一换算修为、检查成就、写库。这样反作弊、修为调平、成就判定都只有一处代码。

## 四、基座一：AudioClock（音频时钟）

这是整个产品的地基。目标：**播放与判定共用同一根时间轴，且已补偿设备输出延迟。**

### 三个必要能力

1. **单一时间源**
   所有事件的调度与记录都用 `audioClock.now()`（音频渲染帧位置换算出的微秒数），不用系统墙钟。

2. **输出延迟标定**
   首次启动做一次静默标定，读取平台报告的 output latency（iOS `AVAudioSession.outputLatency`，Android `AudioTrack.getTimestamp`），存为 `L_out`。
   同时提供"手动校准"入口：播放节拍器，让用户跟拍 16 次，取偏差中位数写入 `L_user`。

3. **判定补偿**
   用户触摸事件带有 `event.timeStamp`（输入时刻），换算到音频时间轴时减去 `L_out + L_user`。

```dart
abstract class AudioClock {
  int nowUs();                       // 当前音频时间（微秒）
  int touchToAudioUs(int rawTouchUs);// 输入时刻 → 补偿后的音频时间
  int get outputLatencyUs;
  Stream<int> beats(int periodUs);   // 采样精度的节拍流
}
```

### EventScheduler

所有"几秒后播一声钟"的需求都提交给它，它按音频时间预排（提前 200ms 预约播放），而不是到点才触发。这样即使 UI 线程卡顿，声音节奏依然精准——这对听潮的呼吸引导尤其重要，节奏一抖用户呼吸就乱。

### SessionRecorder

全程记录 `(音频时间戳, 事件类型)` 的原始序列，落地为一条 session 记录。所有分析（木鱼频率曲线、呼吸同步率、过河与钓花的判定、数雨对账）都是**事后对同一份原始数据做计算**，不在玩法代码里边玩边算。

好处：调参不用改玩法、可以复算历史数据、便于导出调试。

## 五、基座二：修行插件契约

这是"集成式"卖点的落地物。目标：**新增一个修行 = 写一个类 + 一份配置 + 若干音频文件，不改动主程序任何一行。**

```dart
/// 静态描述，用于修行列表展示与筛选
class PracticeManifest {
  final String id;              // 'wooden_fish'
  final String name;            // '木鱼'
  final String subtitle;        // '一百零八声，快慢由心'
  final List<TrainingTag> tags; // 专注/呼吸/耐心/白噪声/助眠
  final EyeMode eyeMode;        // eyesClosed / openThenClosed / eyesOpen
  final Duration typicalLength;
  final int meritBase;          // 基准修为
  final bool needsHeadphones;   // 是否建议耳机
  final String iconKey;
}
```

```dart
/// 运行时逻辑
abstract class PracticeSession {
  Future<void> prepare(PracticeContext ctx); // 预载音频、标定
  void start();
  void onInput(InputEvent e);                // 全屏统一输入
  void onInterrupt(InterruptReason r);       // 来电/通知/后台
  void onResume();
  Future<PracticeResult> finish(FinishReason r);
  Widget buildVisual(BuildContext c);        // 睁眼时看到的画面
  Widget buildSummary(PracticeResult r);     // 结算页
}
```

```dart
/// 统一结算，宿主据此发修为、判成就
class PracticeResult {
  final Duration effectiveDuration; // 有效专注时长（已扣除中断）
  final double quality;             // 0..1，玩法自评的完成质量
  final Map<String, num> metrics;   // 玩法私有指标，存库供曲线用
  final List<Reward> extraRewards;  // 如钓花的花瓣
  final bool completed;
}
```

**配套**：

- `PracticeRegistry`：启动时扫描注册表，生成"修·修行界面"的列表。
- `PracticeContext`：向插件注入 AudioClock、SoundBank、Scheduler、Recorder 与用户偏好，插件不许自己 `new` 这些东西。

**验证插件框架是否合格的方法**：框架完成后，用它实现一个 30 行的"静坐一分钟"最简修行。如果这件事需要改宿主代码，框架就不合格。（这个最简修行同时复用为教程的试玩环节，见[第八节](#八教程声音语言)。）

## 六、主界面规格：三页签、僧页四按钮与打坐

### 6.1 三页签与图标栏

依据框架提示词：左中右三个横向切换页面，屏幕最下方图标栏平移式切换，当前页对应图标放大。

- **左「修」**：修行列表（见[第七节](#七修修行界面与五个修行插件)）。
- **中「僧」**：主界面（本节）。
- **右「我」**：用户界面，**策划案明确暂不开发**，v1 仅占位。

### 6.2 修为条与等级

居中为忙僧立绘；立绘上方是修为条，数字显示为`（当前修为）/（距下一级所需）`，色块长度同比例；再上方是修为等级称号。

| 修为区间 | 等级 |
|---|---|
| 0 – 49 | 浪子 |
| 50 – 199 | 居士 |
| 200 – 499 | 行者 |
| 500 – 999 | 沙弥 |
| 1000 – 1999 | 比丘 |
| 2000 – 4999 | 方丈 |
| 5000 – 9999 | 罗汉 |
| 10000+ | 菩萨 |

（区间边界沿用框架提示词原文；"0–50 浪子、50–200 居士"按半开区间实现，避免边界重叠。）

### 6.3 四个按钮方块（签·成·禅·友）

立绘四周的 Low-Poly 按钮方块：

| 位置 | 按钮 | 功能 |
|---|---|---|
| 左上 | **签** | 每日仅限一次的抽签。点击获得奖励 + 一张写在树叶上的签文 |
| 左下 | **成** | 成就界面。展开成就列表，未解锁的成就灰色显示。判定由宿主结算时统一触发（Domain 层成就引擎） |
| 右上 | **禅** | 进入打坐模式（见 6.4） |
| 右下 | **友** | 好友界面。添加好友、查看已添加好友的修为、与好友交换花瓣。**全 app 唯一强依赖网络的功能**（对应决断 4），走同步引擎 + Supabase Realtime |

**签的奖励口径（待对齐）**：框架提示词为"+10 点修为"，与决断 5（修为只由真实专注时间产生）冲突。两个选项：
a) 保留 +10 修为，作为唯一明示的日常例外；
b) **（建议）改发花瓣或签文收藏**，修为口径保持纯净，签的每日回访价值不变。

### 6.4 打坐（"禅"按钮进入；**非修行插件，不出现在修行列表**）

打坐是主界面上的常驻基础态，由宿主内置实现，不走 `PracticeSession` 插件契约（它没有列表入口、没有结算页，退出即回到主界面）。

- 进入后锁屏式全屏，仅保留忙僧立绘（极低亮度，OLED 省电；框架提示词："屏幕锁定，只剩下忙僧的立绘"）
- 每满 60 秒有效时长 +1 修为，**单日上限 60 点**（上限为本方案新增，防挂机口径见决断 5）
- **反挂机三重判定**（本方案新增，策划案与框架提示词均未涉及）：
  1. app 进入后台立即暂停计时；
  2. 每 5 分钟播放一声极轻的磬，需在 30 秒内轻触任意处确认在场（不确认则暂停计时，不惩罚）；
  3. 陀螺仪检测到持续大幅位移（如走路）暂停计时。
- 退出：长按忙僧立绘 2 秒（策划案/框架提示词只说"长按解除"，2 秒阈值为本方案拟定，防误触）

## 七、修·修行界面与五个修行插件

### 7.1 修行列表交互

依据框架提示词：纵向滑动列表，每种修行的名称写在横向矩形方块里；点击方块立刻滑动使该方块居中，展开修行详细（图标、训练类型、耗时等）与"确定 / 取消"按钮；确定进入修行，取消回列表。

### 7.2 概览

| 修行 | 训练类型 | 眼态 | 单局时长 | 修为规则 | 与初始文件的关系 |

### 1. 木鱼（专注 · 节奏保持）

- **108 下**，目标间隔 1000ms
  ⚠️ 策划案为 300 下/300 秒。本方案改 108（佛家百八之数，单局约 2 分钟更贴碎片时间）；磬声节点（36 的倍数）、结算判定均基于 108。**若改回 300 需同步调整**——决策点。
- **无外部节拍音**（这是关键：节拍必须来自用户内心，否则不是专注训练而是跟拍游戏）
- 过程反馈仅两处：
  - 每 36 下（三分之一）一声极轻的磬；
  - 偏差累积超过阈值时，木鱼音色微微变闷（暗示，不打断）。
- 结算：
  - 总时长与 108 秒的差值 → 心急 / 走神判定（策划案原意：快=心急，慢=走神，保留）；
  - 输出间隔序列曲线；
  - 计算稳定性指标（间隔标准差）。
- 修为：基准 12 点 × quality（quality 由稳定性而非总时长决定——与策划案"按与 300 秒的时间差给修为"相比，稳定性更能刻画"走神"这一真正要练的东西）
- 眼态：全程闭眼

### 2. 数雨（专注 · 双通道计数 + 白噪声）

- 时长 5 分钟，背景为鸟鸣虫鸣白噪声（约 -24dB）
- **雨滴**：平均 13 秒一滴，随机抖动 ±4 秒，总数约 20–24
- **钟声**：平均 30 秒一声，随机抖动 ±8 秒，总数约 9–11
  ⚠️ 策划案原值为"雨滴 1–3 秒一滴、钟声 1–5 秒一声"：按此参数 5 分钟内事件总数可达 100–300 个，超出人的可数范围，任务必然失败。此处为**正确性修正**而非风格偏离。
- 音色必须拉开频段：
  - 雨滴 = 高频短促（2–4kHz，衰减 <150ms）；
  - 钟声 = 低频长尾（200–400Hz 基频，尾音 >2s）。
- **计数输入（本版补充，原规格缺失）**：
  过程中**轻点一次 = 记一滴雨；长按 ≥300ms = 记一声钟**。两种手势均经 InputCapture 打音频时间戳，由 SessionRecorder 事后与实际事件序列对账（误触、漏记均可复算）。
  备选：策划案原意的"结束后询问报数"实现更简单，但丢失过程数据、也无法区分"没听见"和"数错"。默认采用实时计数，待对齐。
- **反作弊**：
  - 雨滴与钟声的最小间隔 800ms，避免同时响导致漏数；
  - 同一分钟内不出现超过 3 个事件。
- 结算：分别报告"你数到 N（来自输入），实际 M"，误差率 ≤10% 判为优秀
- 修为：基准 15 点 × (1 − 平均误差率)，下限 5 点
- 眼态：全程闭眼

---

### 3. 听潮（呼吸 · 助眠）

- 潮汐节奏引导呼吸，默认 4 秒吸 / 6 秒呼（涨潮音渐强 4 秒，落潮音渐弱 6 秒）
- **必须有互动**（否则与"传统冥想缺乏互动性"的产品主张自相矛盾）：吸气时长按屏幕，呼气时松开
  ⚠️ 策划案原文标注"无挑战互动（还可以丰富，我暂时没想好）"——本方案的按压呼吸即是对这个空位的回应。若与玩法负责人（煜）对齐后仍倾向无互动，删去 `onInput` 分支即可，契约上零成本。
- 反馈：
  - 按压与潮汐相位吻合时，潮声中叠入一层极轻的风铃；
  - 偏离时无惩罚、无声音。
- 支持三档节奏：入门 4-6、标准 4-7、深度 4-8（后者接近助眠的生理触发区）
- 结算：呼吸同步率曲线（复用木鱼的曲线组件）+ 平均呼吸周期
- **助眠模式**：勾选后结束不弹结算页，音频渐弱至静音、屏幕保持黑屏，修为次日打开时补发
- 眼态：全程闭眼

### 4. 钓花（耐心 · 收集）

> 原构建方案完全遗漏了此玩法（策划案中由 Radium 负责，与过河同组），本版补全。
> 花瓣图鉴、`PracticeResult.extraRewards` 的注释原本就是为它留的位。

**策划案原机制照录**：长按屏幕甩杆开始垂钓；"叮"= 花瓣碰到钓竿，松手钓起；"咚"= 不是花瓣，无法钓起；花瓣在屏幕上缓慢漂动；甩杆越久，花瓣移向钓竿概率越高；刚甩杆会击散附近的花瓣。钓上来的花瓣永久保存，钓上几朵相同的花瓣可合成一朵花，在图鉴里显示。

本方案规格：

- **玩法循环**：长按甩杆 → 进入"聚瓣期"（触竿概率随本次甩杆时长上升，拟：10 秒约 20% → 60 秒约 60%，参数靠 SessionRecorder 数据调）→ 触竿事件响"叮"（花瓣，拟 65%）或"咚"（杂物，拟 35%）→ "叮"后 1.5 秒内松手收杆钓起；"咚"后松手为空竿 → 松手后 2 秒休竿期，再甩进入下一轮。
- **耐心训练的两个抓手**（策划案机制的直接转译）：
  - 刚甩杆的前 2 秒概率为 0 且"击散"附近花瓣——急躁直接受损；
  - 甩得越久机会越大——但"咚"杂物随等待同步变多，逼用户在"再等等"和"该收手"之间做听觉判断。
- **听觉化改造（按决断 1，需与玩法负责人对齐）**：
  策划案中花瓣漂动、击散都是纯视觉信息，与本产品"闭眼可玩"原则冲突。改造后核心判定全部走听觉（叮/咚），花瓣漂动画面降级为睁眼奖励层——闭眼时它照样在跑，只是不依赖它做判定。
- **反挂机**：连续 90 秒无有效输入（甩杆/松手）自动进入结算；挂机不放杆钓不到任何东西。
- 结算：本局有效时长、钓起花瓣数与种类、"咚"误收次数、平均等待时长；花瓣入库动画在结算页（睁眼奖励）。
- 修为：有效参与分钟数 × 2 × quality（quality 由平均等待时长与误收率构成，防止"速钓刷次数"）⚠️ 策划案未给修为规则，本条为拟定。
- **收集线**：花瓣经 `extraRewards` 返还给宿主，写本地 SQLite 花瓣表；同种花瓣合成一朵花（**合成数量策划案未定，建议 3 朵，待对齐**）；图鉴在 Domain 层花瓣图鉴模块；好友交换花瓣走同步引擎（见 6.3"友"）。
- 眼态：开始时睁眼看规则 → 全程闭眼（同过河）。

### 5. 过河（专注 · 节奏复现）

- 每一跳：先播 `叮 —— 咚`，间隔 T 随机取 0.6–2.0 秒；用户长按屏幕，在自认为 T 之后松开
- 判定窗口：`max(T × 15%, 180ms)`
- 三段判定：
  - 窗口内 = 成功；
  - 窗口 1.5 倍内 = 踩滑（不死，但难度不递进）；
  - 超出 = 失败结束。
- **起手口径（本版澄清）**：按下时刻不设硬判定（以"咚"为计时锚点，起手早晚只计入曲线）；硬判定只有"松手时刻 − 咚实际播放时刻 ≈ T"。与策划案"按照叮和咚的间隔长按再松开"的体感一致：听到叮预备，咚响起时按下。
- 难度递进：每 5 跳，T 的取值范围扩大、并引入"变奏"（叮-咚-咚，需复现第二段间隔）
- 结算：最高连续跳数写入成就（策划案原意保留）；修为 = min(跳数 × 0.6, 20)
- 眼态：开始时睁眼看规则 → 全程闭眼；结算页展示走过的石阶
- **关键实现**：判定用 `touchToAudioUs` 补偿后的时间戳，与"咚"的实际播放音频时间戳相减，**不用长按发生时的系统墙钟时间**。

## 八、教程（声音语言）

策划案分工中有教程模块（Geze）："告知用户哪些声音代表闭眼，哪些代表睁眼，以及怎么积攒修为等"。原构建方案遗漏，本版补全。

产品以声音为第一通道，教程的本质是**教一门声音语言**，建议首启三段式：

1. **声音语义表**（统一由 SoundBank 提供，全 app 一致）：

   | 声音 | 语义 |
   |---|---|
   | 磬一声 | 开始 / 请闭眼 |
   | 磬两声 | 结束 / 可以睁眼 |
   | 极轻的磬 | 打坐在场确认（30 秒内轻触任意处） |
   | 叮 —— 咚 | 过河：间隔度量（复现它） |
   | 叮 / 咚 | 钓花：花瓣 / 杂物（叮则收手） |
   | 木鱼声 | 节拍锚（由用户自己敲出） |

   ⚠️ 注意：叮/咚在过河与钓花中**语义不同**（间隔度量 vs 物件判定），SoundBank 必须用不同音色或包络区分，教程分别教学，否则用户会迁移错误预期。
2. **60 秒试玩**：直接复用第五节那个 30 行的"静坐一分钟"最简修行——教程与框架验收是同一件事。
3. **AudioClock 手动校准**（跟拍 16 次取中位数）嵌入教程最后一步，用户无感知地完成 `L_user` 标定。

修为规则说明放在教程尾页，并在"成"按钮页常驻入口。
