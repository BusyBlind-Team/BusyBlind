## 一、五个前置设计决断

后面所有内容都基于这五条，建议先对齐：

1. **听觉是第一交互通道，视觉是辅助。**
   所有玩法必须在"屏幕熄灭 / 用户闭眼"的前提下成立；屏幕上的内容是"睁眼时的奖励"，不是"闭眼时的必需"。

2. **一切时间以音频时钟为准。**
   不使用帧循环、不使用 `setInterval` 做判定。

3. **修行是插件，不是页面。**
   每个修行实现同一份契约，主程序不认识任何具体修行。

4. **本地优先（local-first）。**
   全部数据先写本地，服务器只是同步与社交层；断网时除加好友外功能完整。

5. **修为只由"真实完成的专注时间"产生。**
   任何可挂机、可后台刷的口子都视为 bug。

## 二、技术栈

**推荐组合：Flutter + 原生音频插件**

| 层面 | 选型 | 说明 |
|---|---|---|
| UI / 逻辑 | Flutter | 单套代码双端；Low-Poly 风格的几何图形用 `CustomPainter` 直接画，比切图省事且分辨率无损 |
| 背景长音轨 | `just_audio` | 潮汐、白噪声等长音频 |
| 短音效 | `soLoud` 或原生 AVAudioEngine / Oboe 封装 | 木鱼声、叮/咚、磬 |
| 本地存储 | SQLite（Drift） | 存修行记录与花瓣；SharedPreferences 只存轻量偏好 |
| 状态管理 | Riverpod | — |
| 后端 | Supabase | Postgres + Auth + Realtime，省掉自建服务器 |

**为什么不选 Unity**：包体大（起步 40MB+），冥想类应用启动速度和体积敏感，而本产品几乎没有 3D 与物理需求。

**为什么不选 React Native / Web**：短音效低延迟触发是本产品的命门，JS 桥接层在这一点上不可靠。

**关键取舍**：短音效播放必须走原生层，且预加载进内存池，禁止播放时解码。木鱼玩法需要支持每秒一次、连续 108 次无卡顿、无音头截断。

## 三、架构分层

```
┌─────────────────────────────────────────────┐
│  Shell 层：三页签容器 / 修·僧·我 导航         │
├─────────────────────────────────────────────┤
│  Practice Host（修行宿主）                   │
│   · 生命周期调度  · 中断恢复  · 结算收口     │
├──────────────┬──────────────┬───────────────┤
│ Practice     │ Practice     │ Practice      │
│ 木鱼         │ 数雨         │ 听潮 …        │  ← 插件
├──────────────┴──────────────┴───────────────┤
│  Core Services（所有修行共用）               │
│   AudioClock  · SoundBank  · EventScheduler  │
│   InputCapture · SessionRecorder · Haptics   │
├─────────────────────────────────────────────┤
│  Domain：修为经济 / 成就引擎 / 花瓣图鉴       │
├─────────────────────────────────────────────┤
│  Data：本地 SQLite  ⇄  同步引擎  ⇄  云端      │
└─────────────────────────────────────────────┘
```

**要点**：修行插件**不允许**直接访问 Domain 层。它只能向宿主返回一份结果对象，由宿主统一换算修为、检查成就、写库。这样反作弊、修为调平、成就判定都只有一处代码。

## 四、基座一：AudioClock（音频时钟）

这是整个产品的地基。目标：**播放与判定共用同一根时间轴，且已补偿设备输出延迟。**

### 三个必要能力

1. **单一时间源**
   所有事件的调度与记录都用 `audioClock.now()`（音频渲染帧位置换算出的微秒数），不用系统墙钟。

2. **输出延迟标定**
   首次启动做一次静默标定，读取平台报告的 output latency（iOS `AVAudioSession.outputLatency`，Android `AudioTrack.getTimestamp`），存为 `L_out`。
   同时提供"手动校准"入口：播放节拍器，让用户跟拍 16 次，取偏差中位数写入 `L_user`。

3. **判定补偿**
   用户触摸事件带有 `event.timeStamp`（输入时刻），换算到音频时间轴时减去 `L_out + L_user`。

```dart
abstract class AudioClock {
  int nowUs();                       // 当前音频时间（微秒）
  int touchToAudioUs(int rawTouchUs);// 输入时刻 → 补偿后的音频时间
  int get outputLatencyUs;
  Stream<int> beats(int periodUs);   // 采样精度的节拍流
}
```

### EventScheduler

所有"几秒后播一声钟"的需求都提交给它，它按音频时间预排（提前 200ms 预约播放），而不是到点才触发。这样即使 UI 线程卡顿，声音节奏依然精准——这对听潮的呼吸引导尤其重要，节奏一抖用户呼吸就乱。

### SessionRecorder

全程记录 `(音频时间戳, 事件类型)` 的原始序列，落地为一条 session 记录。所有分析（木鱼频率曲线、呼吸同步率、过河判定）都是**事后对同一份原始数据做计算**，不在玩法代码里边玩边算。

好处：调参不用改玩法、可以复算历史数据、便于导出调试。

## 五、基座二：修行插件契约

这是"集成式"卖点的落地物。目标：**新增一个修行 = 写一个类 + 一份配置 + 若干音频文件，不改动主程序任何一行。**

```dart
/// 静态描述，用于修行列表展示与筛选
class PracticeManifest {
  final String id;              // 'wooden_fish'
  final String name;            // '木鱼'
  final String subtitle;        // '一百零八声，快慢由心'
  final List<TrainingTag> tags; // 专注/呼吸/耐心/白噪声/助眠
  final EyeMode eyeMode;        // eyesClosed / openThenClosed / eyesOpen
  final Duration typicalLength;
  final int meritBase;          // 基准修为
  final bool needsHeadphones;   // 是否建议耳机
  final String iconKey;
}
```

```dart
/// 运行时逻辑
abstract class PracticeSession {
  Future<void> prepare(PracticeContext ctx); // 预载音频、标定
  void start();
  void onInput(InputEvent e);                // 全屏统一输入
  void onInterrupt(InterruptReason r);       // 来电/通知/后台
  void onResume();
  Future<PracticeResult> finish(FinishReason r);
  Widget buildVisual(BuildContext c);        // 睁眼时看到的画面
  Widget buildSummary(PracticeResult r);     // 结算页
}
```

```dart
/// 统一结算，宿主据此发修为、判成就
class PracticeResult {
  final Duration effectiveDuration; // 有效专注时长（已扣除中断）
  final double quality;             // 0..1，玩法自评的完成质量
  final Map<String, num> metrics;   // 玩法私有指标，存库供曲线用
  final List<Reward> extraRewards;  // 如钓花的花瓣
  final bool completed;
}
```

**配套**：

- `PracticeRegistry`：启动时扫描注册表，生成"修·修行界面"的列表。
- `PracticeContext`：向插件注入 AudioClock、SoundBank、Scheduler、Recorder 与用户偏好，插件不许自己 `new` 这些东西。

**验证插件框架是否合格的方法**：框架完成后，用它实现一个 30 行的"静坐一分钟"最简修行。如果这件事需要改宿主代码，框架就不合格。

## 六、五个修行的完整规格

### 概览

| 修行 | 定位 | 眼态 | 时长 | 修为规则 |
|---|---|---|---|---|
| 打坐 | 基础态 · 常驻（非插件） | 熄屏，仅剪影 | 不限 | 每满 60 秒有效 +1，单日上限 60 |
| 木鱼 | 专注 · 节奏保持 | 全程闭眼 | 108 下 | 12 × quality |
| 数雨 | 专注 · 双通道计数 + 白噪声 | 全程闭眼 | 5 分钟 | 15 × (1 − 误差率)，下限 5 |
| 听潮 | 呼吸 · 助眠 | 全程闭眼 | 自定（三档节奏） | 规格未给公式；助眠模式次日补发 |
| 过河 | 专注 · 节奏复现 | 开局睁眼 → 闭眼 | 由跳数决定 | min(跳数 × 0.6, 20) |

---

### 1. 打坐（基础态，非插件，常驻）

- 进入后锁屏式全屏，仅保留忙僧剪影（极低亮度，OLED 省电）
- 每满 60 秒有效时长 +1 修为，**单日上限 60 点**
- **反挂机三重判定**：
  1. app 进入后台立即暂停计时；
  2. 每 5 分钟播放一声极轻的磬，需在 30 秒内轻触任意处确认在场（不确认则暂停计时，不惩罚）；
  3. 陀螺仪检测到持续大幅位移（如走路）暂停计时。
- 退出：长按忙僧 2 秒

---

### 2. 木鱼（专注 · 节奏保持）

- **108 下**，目标间隔 1000ms
- **无外部节拍音**（这是关键：节拍必须来自用户内心，否则不是专注训练而是跟拍游戏）
- 过程反馈仅两处：
  - 每 36 下（三分之一）一声极轻的磬；
  - 偏差累积超过阈值时，木鱼音色微微变闷（暗示，不打断）。
- 结算：
  - 总时长与 108 秒的差值 → 心急 / 走神判定；
  - 输出间隔序列曲线；
  - 计算稳定性指标（间隔标准差）。
- 修为：基准 12 点 × quality（quality 由稳定性而非总时长决定，避免"故意拖慢刷时长"）
- 眼态：全程闭眼

---

### 3. 数雨（专注 · 双通道计数 + 白噪声）

- 时长 5 分钟，背景为鸟鸣虫鸣白噪声（约 -24dB）
- **雨滴**：平均 13 秒一滴，随机抖动 ±4 秒，总数约 20–24
- **钟声**：平均 30 秒一声，随机抖动 ±8 秒，总数约 9–11
- 音色必须拉开频段：
  - 雨滴 = 高频短促（2–4kHz，衰减 <150ms）；
  - 钟声 = 低频长尾（200–400Hz 基频，尾音 >2s）。
- **反作弊**：
  - 雨滴与钟声的最小间隔 800ms，避免同时响导致漏数；
  - 同一分钟内不出现超过 3 个事件。
- 结算：分别报告"你数到 N，实际 M"，误差率 ≤10% 判为优秀
- 修为：基准 15 点 × (1 − 平均误差率)，下限 5 点
- 眼态：全程闭眼

---

### 4. 听潮（呼吸 · 助眠）

- 潮汐节奏引导呼吸，默认 4 秒吸 / 6 秒呼（涨潮音渐强 4 秒，落潮音渐弱 6 秒）
- **必须有互动**（否则与"传统冥想缺乏互动性"的产品主张自相矛盾）：吸气时长按屏幕，呼气时松开
- 反馈：
  - 按压与潮汐相位吻合时，潮声中叠入一层极轻的风铃；
  - 偏离时无惩罚、无声音。
- 支持三档节奏：入门 4-6、标准 4-7、深度 4-8（后者接近助眠的生理触发区）
- 结算：呼吸同步率曲线（复用木鱼的曲线组件）+ 平均呼吸周期
- **助眠模式**：勾选后结束不弹结算页，音频渐弱至静音、屏幕保持黑屏，修为次日打开时补发
- 眼态：全程闭眼

---

### 5. 过河（专注 · 节奏复现）

- 每一跳：先播 `叮 —— 咚`，间隔 T 随机取 0.6–2.0 秒；用户长按屏幕，在自认为 T 之后松开
- 判定窗口：`max(T × 15%, 180ms)`
- 三段判定：
  - 窗口内 = 成功；
  - 窗口 1.5 倍内 = 踩滑（不死，但难度不递进）；
  - 超出 = 失败结束。
- 难度递进：每 5 跳，T 的取值范围扩大、并引入"变奏"（叮-咚-咚，需复现第二段间隔）
- 结算：最高连续跳数写入成就；修为 = min(跳数 × 0.6, 20)
- 眼态：开始时睁眼看规则 → 全程闭眼；结算页展示走过的石阶
- **关键实现**：判定用 `touchToAudioUs` 补偿后的时间戳，与"咚"的实际播放音频时间戳相减，**不用长按发生时的系统墙钟时间**。
